01

ARCHITECTURE

一個儲存庫，串起完整網站

GitHub 保存程式碼；Cloudflare Workers 提供前端與後端；D1 保存網站資料。

前端檔案與 API 可以放在同一個 GitHub 儲存庫、同一個 Workers 專案，一起部署。D1 則是另外建立、再綁定給 Worker 的資料庫資源。[1][3]

如果是新專案，建議採用 Workers Static Assets＋Workers API＋D1。Cloudflare 目前也建議新專案優先使用 Workers，原有 Pages 專案仍可繼續使用。[2]

平台提供環境，功能由你的程式完成。

Workers 執行你寫的 API 與業務規則；D1 不會自動替網站建立登入、會員權限或管理後台。

元件負責什麼你要準備什麼
GitHub版本管理與部署來源前後端程式、部署設定、migration、套件鎖檔
Workers Static Assets提供 HTML、CSS、JavaScript 等前端檔案前端建置結果，例如 dist/
Workers API接收請求、檢查輸入與權限、執行業務規則API 路由與後端程式
D1保存與查詢 SQL 資料資料表、索引、查詢與結構變更紀錄
02

REQUEST FLOW

畫面與資料庫之間，由 API 接手

以任務清單為例，瀏覽器呼叫 GET /api/tasks，Worker 查詢 D1，再把結果以 JSON 回傳。前端收到資料後，才把任務畫在頁面上。[3]

Binding（資源綁定）負責把指定資料庫交給 Worker 使用。例如設定綁定名稱為 DB，程式就透過 env.DB 執行查詢。[4]

新增任務時，前端把內容送到寫入 API；Worker 先確認輸入與操作權限，再執行 SQL。正式資料保存在 D1，前端只取得 API 允許回傳的內容。

D1 使用 SQLite 的 SQL 語意。

它是由 Cloudflare 管理的資料庫；把一個 .db 檔案提交到 GitHub，並不會因此建立 D1。[3]

03

IMPLEMENTATION

六個步驟，接上第一個 D1 API

以下是設定範例，假設你已有使用 npm 的 React／Vue＋Vite 專案，前端建置輸出為 dist/。

指令在具備 Node.js、npm 的專案目錄中執行。若使用 Next.js 等含伺服器端功能的框架，應採用對應的 Cloudflare 部署方式，再接上 D1；不要直接覆蓋框架產生的設定。[14]

1 · 安裝並登入 Wrangler

Wrangler 是 Cloudflare 的命令列工具，用來本機開發、管理 D1 與部署 Workers。[3]

終端機 · 專案目錄
npm install -D wrangler@latest
npx wrangler login

2 · 建立 D1 資料庫

終端機 · 建立雲端資料庫
npx wrangler d1 create my-app-db

記下回傳的 database_id。若 Wrangler 已協助新增資料庫設定，檢查內容即可，避免重複加入同一個 Binding。[3]

3 · 設定前端、後端與資料庫綁定

在專案根目錄建立或調整 wrangler.jsonc，並把資料庫 ID 換成實際值。

wrangler.jsonc
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "my-app",
  "main": "worker/index.js",
  "compatibility_date": "2026-10-20",

  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/*"]
  },

  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "my-app-db",
      "database_id": "替換成你的 database_id",
      "migrations_dir": "migrations"
    }
  ]
}
設定用途
main後端程式的入口檔案。
assets.directory前端建置輸出目錄，必須與專案實際結果一致。
single-page-application支援前端路由，例如直接開啟 /settings。
run_worker_first讓 /api/* 先交給 Worker，避免被前端頁面接走。
binding: "DB"把資料庫提供給後端的 env.DB。

前端路由與 Assets 綁定依 Workers 官方設定；D1 綁定與 migration 目錄放在同一份設定檔中。[17][15]

4 · 用 migration 建立資料表

Migration 是有版本紀錄的資料庫結構變更檔。把它提交到 GitHub，就能追蹤每次新增的資料表或欄位；D1 會記錄哪些檔案已經套用。[15]

終端機 · 產生帶版本編號的 SQL 檔
npx wrangler d1 migrations create my-app-db create_tasks

在產生的 SQL 檔中填入以下範例。這筆初始任務只是串接測試資料。

migrations/ · 新產生的 SQL 檔
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL
);

INSERT INTO tasks (title)
VALUES ('完成第一個 Cloudflare 與 D1 串接');

5 · 寫出查詢任務的後端 API

建立 worker/index.js。以下程式提供 GET /api/tasks，其他網頁請求交給前端檔案處理。[5][17]

worker/index.js
export default {
  async fetch(request, env) {
    const { pathname } = new URL(request.url);

    if (pathname === "/api/tasks" && request.method === "GET") {
      const { results } = await env.DB
        .prepare(
          "SELECT id, title FROM tasks ORDER BY id DESC LIMIT 50"
        )
        .all();

      return Response.json(results);
    }

    if (pathname.startsWith("/api/")) {
      return Response.json(
        { error: "找不到此 API" },
        { status: 404 }
      );
    }

    return env.ASSETS.fetch(request);
  }
};

6 · 在前端讀取資料

把取得的 tasks 交給前端元件顯示。同一個網站可直接使用相對路徑 /api/tasks。

前端 · 讀取任務的程式片段
const response = await fetch("/api/tasks");

if (!response.ok) {
  throw new Error("讀取任務失敗");
}

const tasks = await response.json();

新增、修改、刪除也由 Worker 提供對應 API。帶入使用者輸入時，使用參數綁定；以下是寫入邏輯片段，尚未包含完整的 POST 路由。[3]

Worker · 參數化寫入範例
// title 應先經過輸入檢查與操作權限確認
await env.DB
  .prepare("INSERT INTO tasks (title) VALUES (?)")
  .bind(title)
  .run();

.bind() 把輸入當成參數，避免直接拼接 SQL 造成 SQL injection；它不會取代輸入驗證或使用者權限檢查。[3]

04

LOCAL & REMOTE

同一份結構，兩份不同的資料

--local 與 --remote 指向不同環境；本機資料不會隨程式部署自動同步到正式 D1。[3]

先在本機套用 migration，確認 API 能查到測試資料，再對正式 D1 套用相同的結構變更。部署 Worker 與建立資料表，是兩個需要分別完成的動作。

未來若增加預覽或測試環境，應使用獨立資料庫與綁定，避免測試操作寫進正式資料。

先確認本機可運作

終端機 · 本機開發
npm run build
npx wrangler d1 migrations apply my-app-db --local
npx wrangler dev

開啟 Wrangler 顯示的本機網址，在後面加上 /api/tasks，確認能看到剛才的測試資料。前端檔案改動後，依本範例重新建置 dist/。

再建立正式資料表並部署

終端機 · 正式環境
npx wrangler d1 migrations apply my-app-db --remote
npx wrangler deploy

部署後，使用 Wrangler 提供的正式網址，再檢查一次 /api/tasks。Migration 只會套用尚未執行的變更。[6]

05

GITHUB → DEPLOYMENT

推送程式碼，觸發正式部署

第一次手動部署成功後，把程式、設定、migration 與套件鎖檔提交到 GitHub，再把既有 Worker 連接儲存庫。[7]

  1. 進入 Cloudflare 的 Workers & Pages。
  2. 選擇剛才部署的 my-app。
  3. 進入 Settings → Builds → Connect。
  4. 連接 GitHub，選擇儲存庫。
  5. 設定正式分支、建置指令與部署指令。
名稱必須一致。

Cloudflare 上的 Worker 名稱，要與 wrangler.jsonc 的 name 相同，否則建置會失敗。[7]

項目本範例設定作用
正式分支main此分支的推送觸發正式部署。
Root directory專案根目錄若專案在子資料夾，填入對應路徑。
Build commandnpm run build產生前端建置結果。
Deploy commandnpx wrangler deploy部署 Worker 與前端資源。

Build command 與 Deploy command 是兩個階段；建置時使用的環境變數與密鑰，也不會自動成為 Worker 執行時的設定。執行時密鑰應設在 Worker 的 Variables & Secrets。[8]

讓 migration 一起自動化

希望正式部署時自動更新資料表，就把 Deploy command 改為：

Cloudflare Builds · 正式 Deploy command
npx wrangler d1 migrations apply my-app-db --remote && npx wrangler deploy

&& 表示 migration 成功後，才繼續部署程式。這個指令放在正式部署流程；預覽環境應使用自己的資料庫與設定。

自動更新 D1，需要部署權杖有寫入權限。

為部署用的 API Token 加上目標帳號的 D1 Edit／寫入權限。官方目前列出的自動產生 Token 預設權限未包含 D1，可到 My Profile → API Tokens 調整。[8][16]

Migration 與程式部署不是同一個原子操作：如果 migration 成功、部署卻失敗，資料庫變更仍可能已生效。刪除欄位或改變資料格式時，應分階段調整，讓新舊程式在交接期間都能運作；程式回滾也不會自動回復資料庫。

06

COST & CAPACITY

可以免費起步，先看懂用量怎麼算

截至 2026 年 10 月 20 日，D1 免費方案的主要額度如下。不同計量單位分開閱讀，不能直接拿 API 次數換算資料庫額度。[11][12]

項目D1 免費方案理解重點
單一資料庫容量500 MB一個資料庫的容量上限。
帳號內總容量5 GB帳號內各資料庫合計上限。
每日讀取額度500 萬列計算查詢讀取／掃描的資料列。
每日寫入額度10 萬列新增、修改與刪除都會計入。

一次 API，不一定只讀一筆

假設資料表有 5,000 列，查詢未利用索引而掃過全表，即使只回傳一筆結果，也可能計入 5,000 列讀取。資料變多後，應針對常用查詢建立索引。[11]

付費方案也有容量與用量限制

Workers Paid 最低為 每月 US$5，超出內含用量可能另計費。Workers 另有自己的請求與運算額度；付費 D1 的單一資料庫上限為 10 GB。[13][12]

以一般資料新增、查詢、修改、刪除為主的網站、管理後台或 MVP，這套架構值得優先評估。若單一資料庫預期超過 10 GB，或需要持續大量同時寫入，應先評估分庫與吞吐量；單一 D1 資料庫會依序處理查詢。[12]

07

READY TO VERIFY

先確認三件事，再驗收整條串接

後端與套件相容性

Workers 提供部分 Node.js API，需要檢查既有套件是否支援。原本直接開啟本機 SQLite 檔案的程式，必須改成 D1 存取介面。[10]

登入、權限與輸入檢查

有會員、管理員或私人資料時，API 必須確認「目前是誰」及「可以操作哪些資料」。前端隱藏按鈕，只影響畫面，不能取代後端授權。

密鑰與資料保存位置

第三方 API Key 等密鑰放在 Workers Secrets。本機的 .env、.dev.vars 不提交到 GitHub；GitHub 保存程式與結構變更，正式資料由 D1 保存。[9]

第一階段完成標準

  1. 網站能讀到 D1 資料。前端、Worker API 與資料庫 Binding 已接通。
  2. 推送 GitHub 後，網站自動更新。儲存庫、建置指令與部署流程已接通。
  3. 重新部署後，既有資料仍保留。程式更新與正式資料保存已正確分開。

本頁為架構與設定範例。實際目錄、框架設定與部署指令，應配合你的專案內容調整。
